# Implementation Plan: Phase 3 — Business Operations

**Branch**: `003-business-operations` | **Date**: 2026-09-02 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/003-business-operations/spec.md`

---

## Summary
Implement the core transactional business engine for RetailOS: Suppliers & Representatives, Customers & Credit Balances, Purchases & Goods Receipts, Point of Sale (POS) checkout with Weighted Average Cost (WAC) COGS and race-condition protection, Customer & Supplier Payments, Operating Expenses, and Cash Register ledger with daily reconciliation. All ledger patterns are append-only; stock mutations use pessimistic row locking to prevent oversell, and high-risk endpoints (`/api/sales`, `/api/purchases`, `/api/payments`) enforce idempotency keys.

---

## Technical Context

**Language/Version**: C# 13 / .NET 9 LTS  
**Primary Dependencies**: ASP.NET Core Web API, EF Core 9, Npgsql.EntityFrameworkCore.PostgreSQL, FluentValidation, MediatR (or direct service injection conforming to KISS), Serilog  
**Storage**: PostgreSQL 18 (Local connection: `detergents_shop`, `retailos_test`)  
**Testing**: xUnit, FluentAssertions, `WebApplicationFactory` with live PostgreSQL database (disable test parallelization for shared DB testing)  
**Target Platform**: Windows / Linux server  
**Project Type**: ASP.NET Core Web API (Modular Monolith)  
**Performance Goals**: POS sale completion under 60 seconds; barcode and product lookup under 200ms; atomic inventory mutations  
**Constraints**: 
- Decimal precision `numeric(19,4)` for currency amounts; `numeric(19,6)` for unit costs / WAC intermediate calculations.
- Soft-delete on entities with history (`SoftDeletableEntity`); approved transactions are immutable and must be reversed rather than deleted.
- Multi-tenant data isolation via `HasQueryFilter` and `TenantSaveChangesInterceptor`.
- Pessimistic row locking on product rows for sales/stock deductions.
- Idempotency key evaluation for repeated POSTs.
**Scale/Scope**: Single modular monolith codebase; 18 new database entities/tables across 7 business operation submodules.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- [x] **Absolute Constraints**: Correctness (deterministic WAC and ledger math), Security (JWT roles: Cashier, Manager, Owner), Tenant Isolation (all entities implement `ITenantEntity` with global query filters).
- [x] **Simplicity First (KISS)**: Modular monolith services directly injected; no event sourcing or microservices; simple append-only ledger tables.
- [x] **Financial Ledgers**: Supplier, Customer, and Cash Register use transaction ledgers (`SupplierAccountTransaction`, `CustomerAccountTransaction`, `CashRegisterTransaction`).
- [x] **Costing**: Weighted Average Cost (WAC) strictly calculated on purchases and sealed into `SaleLineItem.UnitCost`.
- [x] **Concurrency & Idempotency**: Pessimistic locking on product rows; `IdempotencyRecord` table backing `Idempotency-Key` header on Sales, Purchases, Payments.
- [x] **Soft-Delete Guard**: Suppliers and Customers with history cannot be deleted (returns `409 Conflict`).
- [x] **Human Review Gate**: Sales and Payments modules require verification before production merge.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Idempotency table & header validation | Enforced by Constitution for `/api/sales`, `/api/purchases`, `/api/payments` | In-memory token store does not survive restarts or scale |
| Pessimistic row locking on products | Guarantees zero oversell with multi-cashier contention | Optimistic concurrency causes painful user retry loops at retail checkout |
